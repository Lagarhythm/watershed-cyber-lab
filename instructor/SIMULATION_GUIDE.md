# Watershed Incident Command — simulation guide

The default student experience is now `Watershed_Simulation.ipynb`, served with Voilà via `python launch.py`. It is a live visual incident simulator: no Python cells, no manual Run All step, and no separate development tools for students. The original notebook remains an optional deeper coding lesson.

## Teach the simulation in 15–25 minutes

1. **Brief / 2 min:** open the question-mark briefing. Explain the fictional clock: one real second advances ten simulated seconds at 1×; 4× is available. Start and pause freely. Switching away from the browser tab pauses virtual time.
2. **Observe / 3 min:** select each host on the topology. Watch the event stream and Traffic pulse. At 09:15, sync_agent makes its first connection. Compare the backup workstation; periodicity alone is not evidence of compromise.
3. **Investigate / 5 min:** pause and open Evidence lab. Verify files against the trusted manifest; decode the changed artifact. Match its host, process and destination to an observed stream. Change the hash experiment text and watch individual digest characters change.
4. **Contain / 3 min:** isolate research-07. Resume briefly and see its outbound connections stop. Service availability drops by 25 percentage points. Discuss why isolating everything can be harmful. Restore it before removal to demonstrate that isolation did not remove the process.
5. **Repair / 4 min:** in Portal workbench, try the ordinary name, insert the test payload, and run the original design: all three users match. Select bound parameters and run the same input: no user matches. Try `o'neil` as a legitimate name. Apply the repair. Explain that preventing new malformed logins does not stop the already-running workstation process.
6. **Recover / 3 min:** with evidence preserved and research-07 isolated, remove the simulated process. Restore the host. Traffic stays stopped and availability returns to 100%.
7. **Debrief / 5 min:** finish the attempt and download its JSON report. Compare the decision timeline with another attempt. Ask which observations establish change, access or communication, and which do not establish exfiltration.

A successful run observes at least one connection before containment, verifies and decodes evidence, correlates it, contains research-07, repairs the portal, removes the process while isolated, and restores service. If a learner isolated before any traffic was observed, they can restore and briefly observe in this fictional sandbox. In a real response, do not restore a compromised host just to satisfy an assessment; request previously collected telemetry instead. This is a teaching sequence rather than a universal incident-response playbook.

## What changes, and why

| Interaction | Visible consequence | Learning objective |
|---|---|---|
| Start / pause / change speed | Clock, events and traffic chart advance together | Control observation time and compare event order |
| Click host | Inspector shows its role and actions | Scope an investigation to a system |
| Isolate host | Route animation stops; availability drops | Understand containment tradeoffs |
| Restore before removal | Suspicious traffic can resume | Distinguish containment from remediation |
| Verify files | Actual SHA-256 comparison marks one changed file | Establish integrity without guessing intent |
| Decode artifact | Account, process, host and event clue appear | Recognize reversible encoding |
| Check correlation | Three evidence objectives become complete | Use multiple fields rather than visual suspicion alone |
| Edit hash text | Digest cells highlight changes | Explore determinism and input sensitivity |
| Change query design | Same input produces different database results | Understand code/data separation without Python syntax |
| Apply portal repair | Later malformed logins are rejected | Distinguish entry-point repair from process removal |
| Remove process / restore | Containment persists while availability recovers | Demonstrate a deliberate recovery sequence |
| Finish / export | Objective score and action timeline | Reflect on evidence and decisions |

## Model and assessment boundaries

All network activity is generated by `simulator/engine.py`; it never contacts a destination. The historical file/log evidence comes from the original synthetic packet. The app shows system events available through 09:14, then simulates alternative futures from that point. It does not replay the later fixed network/file-access CSVs as if they were inevitable.

Every six ticks (one simulated minute), an active sync_agent sends a 128-byte modeled connection. Every eighteen ticks, a new malformed portal login is attempted. At tick 54 (09:23), the model attempts sensitive-file access. The scenario window stops at tick 72 (09:26); students can finish evidence work afterward. Routine chart counts are illustrative background traffic.

**Explicit simplification:** isolating research-07 also prevents the scheduled file-read event in this model. Actual network isolation does not prevent local file access. Route animation represents activity, not packet-level timing. Service availability is an illustrative weighted model: research-07 25%, research-08 20%, portal 45%, archive 10%.

Objective score: evidence 60 (20 each for scan, decode and correlation), current containment/removal 15, portal repair 15, and safe restoration 10 (process removed, no hosts isolated). It is a formative checklist, not a validated measure of incident-response competence. A late response can complete the checklist; the debrief separately records whether sensitive-file access already occurred. Hints have no score penalty. Discussion should consider timing and unnecessary service disruption alongside the number.

## Session handling and deployment

Each widget has its own Python Simulation instance. Voilà starts a kernel for the application session. The browser stores a replayable decision journal in localStorage under `watershed-simulation-v2`; a fresh page offers Resume saved attempt, which reconstructs state and pauses. Browser storage is scoped to the browser profile and origin (host/port), not an authenticated learner. Use one browser profile per learner; avoid concurrent tabs writing the same save. There is no central roster, live cohort analytics or LMS grade passback in this app.

Reset asks for confirmation. Report export includes observations, actions and results; user-entered query/hash experiments are local. Do not enter real credentials or personal data. There are no AI calls or external JavaScript/CDN dependencies. Serving it on loopback through Web Desktop or an SSH tunnel is the supported individual demo launch. For a cohort, use authenticated per-user Hub deployment rather than exposing the standalone development port.

## How the implementation works

- `launch.py` and `jupyter/`: start Voilà using a bundled template without CDN font requests.
- `Watershed_Simulation.ipynb`: one source-hidden cell constructs the widget; Voilà hides source by default and runs it on launch.
- `simulator/engine.py`: deterministic Python state, observed events, SHA-256, Base64, in-memory SQLite, actions and scoring.
- `simulator/widget.py`: anywidget state synchronization and messages between browser and kernel.
- `simulator/app.js`: local HTML/SVG controls, chart, keyboard-accessible host buttons, clock scheduler, browser persistence and download.
- `simulator/style.css`: scoped responsive dashboard styles, visible focus, reduced-motion support, status text in addition to color.
- `build_simulation.py`: regenerates the thin starter notebook.

The JavaScript sends a tick each second only while running, and waits for the kernel response before sending another. Background-tab detection pauses the model. Simulation time is intentionally controlled rather than a real-world timer. Evidence and query actions run in Python; changing the interface alone does not execute shell commands or modify the VM.

## Adapt it

For a new incident, revise `HOSTS`, event timing and `dispatch` actions in the engine; revise the corresponding labels, selectors and model explanation in the UI. For a new discipline, keep the select → observe → intervene → debrief loop and substitute meaningful domain consequences. For example, a sensor fault changes a process chart and stopping the affected machine changes production availability.

Add a new action by implementing its state transition in `dispatch`, exposing its result in `snapshot`, adding a UI control that sends that action, and writing a behavior test. Keep graphics tied to state transitions rather than decorative animation. Update scoring and facilitation together. If changing replay semantics, version the localStorage key so an old journal does not silently replay into a different scenario.

Use the older build/customization guides for the original notebook's pandas explorers and editable Python exercises. Those modules are still useful for follow-up technical instruction; they are no longer the main student simulation surface.
